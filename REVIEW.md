## What was built
- **Variable-timing contract first:** `FrameSource` (frameCount, per-frame `frameDuration`, file `loopCount`, `drawFrame`, `ready`), `resolveLoops` (option > file > once), `Ticker` on prefix sums (still skips, 12 old tests unchanged + 9 new), shared `Viewport` extracted from `SvgaRenderer`.
- **`AnimatedImageRenderer`** for GIF / WebP with four decoding paths: WebCodecs `ImageDecoder` (VideoFrame ring, look-ahead 3), own **GIF decoder** (parser + LZW + disposal 1/2/3 compositor, 2.2 KB gz), own **animated-WebP ANMF path** (re-wrap each frame as a still WebP, `createImageBitmap`, composite with offsets / blend / dispose, 1.2 KB gz), still images (`staticDurationMs`, default 2000, then `end`). `path: 'auto'` picks; every path is also forceable.
- **Runtime self-tests** (`selftest.ts`, 74-byte GIF + 140-byte WebP) decide whether the browser's `ImageDecoder` can be trusted. 28 synthetic GIF/WebP files (`samples/synthetic/`, generated by `npm run gen:synthetic`), Playwright harness (`npm run verify:images`), compare page with ours | native `<img>`, scrubber and "path used" label.

## Decisions taken
- **Own GIF decoder instead of `gifuct-js`:** a block parser is needed anyway for frame count / delays / loops without decoding pixels; only ~60 lines of LZW were missing; no dependency; bit-exact vs Chromium on every file.
- **ANMF-wrap works, so there is no `<img>` fallback.** Needs `createImageBitmap` for WebP only (Safari 14+).
- **Delay rule: <= 10 ms is shown as 100 ms, applied by us on every path.** Loop count normalised to total plays (GIF N -> N+1, WebP N -> N, absent GIF -> 1); the player option wins over the file (logged in PROGRESS.md).
- **`auto` uses behaviour self-tests instead of UA sniffing**, because Playwright WebKit's `ImageDecoder` is wrong in two ways (below).
- Background colours ignored (dispose-to-background = transparent, like browsers); GIF disposal 4-7 = leave; any one-frame image uses `createImageBitmap`.
- New opt-in `SvgaRenderer` option `imageSmoothing` (default unchanged) used for the corpus investigation. `playwright` added as a devDependency (as requested; Chromium was already cached; Firefox and WebKit builds downloaded with your approval).

## Flags / questions for reviewer
1. **IMPORTANT, SVGA, found by the real corpus: 14 of 16 real `.svga` files are above the 2 % threshold** (mean 2.1-14.4 %, max up to 15.7 %; the two large `119040-*` files are exact). **Proven cause for all 14: Chromium filters shrunk `<img>` sources better than `ImageBitmap` sources, so our heavily shrunk particle sprites look aliased/sparkly** (zoom shows crisp single pixels vs the reference's smooth ones). Giving our renderer `<img>` elements instead gives 0.000-0.003 % on the worst files at about the same cost (5.2 vs 4.4 ms on Pink-Heart-Rocket). `imageSmoothingQuality = 'medium'` is NOT the fix (half the error, 2.4x slower, 13 files still over). **Decision needed:** switch `decodeSvgaImages` to decoded `<img>` elements (no `close()`, browser-managed decode cache, DOM-bound), or keep ImageBitmap and accept lower minification quality. I did not change it unilaterally. Not tested in Safari/Firefox. Details: `reports/corpus.md`, PROGRESS.md addendum.
2. **WebKit's `ImageDecoder` (Playwright WebKit 27.2) is wrong for GIF and WebP with transparency:** "restore to background" comes out opaque black; partially transparent WebP frames come out opaque and get *more* wrong each time a frame is decoded again (loop 2 would differ from loop 1). Chromium is right. `auto` routes around both by self-test; the forced `imagedecoder` rows in the table are "known". Real iOS devices were not tested.
3. **Firefox is unverified:** the Playwright Firefox 157 build exits immediately ("Could not find profile folder"; fresh download, sandbox-free run and local profile all tried). It has no `ImageDecoder`, so it would use the own decoders, which are plain canvas / `createImageBitmap` code; that is an inference, not a measurement.
4. **Clamp rule evidence:** verified in WebKit through `ImageDecoder`; in Chromium its `ImageDecoder` reports raw delays (the clamp lives in its image layer). I could not observe native `<img>` frame timing headlessly, so Chromium `<img>` and Firefox rely on documented behaviour.
5. Chromium forced `imagedecoder` on a single-frame lossy still shows Δ up to 37/255 colour (YUV conversion); `auto` never uses that combination. WebKit passes it.
6. Real GIF note: `rotating-earth.gif` declares 65535 repeats (65,536 plays): effectively forever but not 0.
7. Limits: GIF rewinds replay from frame 0 (loops are free); `verify:corpus` skips extensionless / PNG corpus files; replaceable-key detection flags `HeadSHine*` (false positives); PNG/APNG unsupported.

## Verification summary
- **Timing** (2 plays, 6 files, both forced paths, Chromium and WebKit): every frame appears within **<= 18 ms** (one rAF tick) of its scheduled start; total play time within 17 ms of the sum of the delays. **Loops:** 14/14 per browser (0/1/3/absent for both formats, option beats file, forever, still images end after `staticDurationMs`).
- **Leaks** (50 create -> play -> seek -> destroy cycles per path, 4 files x 2 paths x 2 browsers): VideoFrames, ImageBitmaps and decoders created = closed in every row; rAF outstanding 0; ResizeObservers live 0. Peak open per renderer: ImageDecoder 4-8 VideoFrames (100-frame WebP: 8), ANMF 3 bitmaps, GIF fallback 0 (a single RGBA buffer), independent of frame count.
- **Bundle** (min+gzip): image renderer 11 KB (shares detection + fflate with SVGA), GIF decoder 2.2 KB, WebP parser 1.2 KB, Ticker 0.8 KB; SVGA 11.5 KB; both 18 KB.
